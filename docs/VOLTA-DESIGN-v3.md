## 0. 三个必须先纠正的判断

### 0.1 修正一：帧传输方案要换

v1/v2 我定的是「mpv 独立进程 + D3D11 共享纹理」。查完 mpv 的 `render_d3d11.h` 原文后发现问题：

```
mpv_d3d11_init_params.device  →  调用方提供 ID3D11Device
mpv_d3d11_fbo.tex              →  调用方提供 ID3D11Texture2D
```

**device 和纹理都归调用方所有。** 这是**嵌入 API** 的约定——意味着这套 D3D11 接口设计上就是给「同一进程内的 libmpv」用的，不是给「跨进程」用的。

跨进程要共享纹理，得走 D3D11 的 shared handle + keyed mutex，而 mpv 侧**不导出 device 也不导出纹理句柄**，我们无从拿到要共享的那个 ID3D11Device。**跨进程 D3D11 共享纹理这条路在 mpv 现有 API 下走不通。**

改用另一条已验证的路：

| 方案 | 帧怎么来 | 画质 | 状态 |
|---|---|---|---|
| A. 跨进程 D3D11 共享纹理 | 做不到 | — | **废弃** |
| **B. `--wid` 原生窗口嵌套** | mpv 自己画进父窗口 | **完整 gpu-next** | **Windows 主选** |
| C. 进程内 libmpv + `render_context` | 回调渲染进我们给的纹理 | 老 vo_gpu，**无 libplacebo** | 备选 |

**B 的依据**（mpv-examples/libmpv README 原文）：libmpv 支持 `wid` 选项，把自己的视频窗口挂到我们提供的窗口下。win32 上可行。而 iptvnator 项目在 Windows 上就是这么干的：`CreateWindowEx` 建子 HWND → `mpv_set_option("wid")` → `SetWindowPos` 定位。

**B 的代价**（iptvnator 实测踩过的坑，doc 里写得很明白）：native surface stacking 意味着**原生窗口永远盖在 DOM/UI 之上**，控制条、弹窗要靠「挖洞 + 独立 overlay 窗口」这套复杂机制。iptvnator 最终放弃这条路，全面转向帧拷贝（spikes/mpv-frame-copy）。

### 0.2 修正二：既然共享纹理走不通，性能预算要重算

帧拷贝（CPU 通道）的实测预算（1080p BGRA8）：

| 路径 | 带宽 | 16 GB/s 机器占比 |
|---|---|---|
| 1 路 1920×1080@60 | 475 MB/s | 3.0% |
| 9 路 760×428@60 | 670 MB/s | 4.2% |
| **9 路背景 + 1 路焦点，合计** | **1145 MB/s** | **7.2%** |
| （若背景格错按 1080p 渲染）9 路 | 4271 MB/s | 26.7% |

**结论没变，反而更硬**：按显示尺寸渲染省下的不是「一点」，是 **6 倍**。帧拷贝路径在 9 路下完全跑得动，前提是背景格不按源分辨率渲染。

### 0.3 修正三：HDR 与网格多路是互斥的

Windows 上 HDR 直通必须全屏独占（`d3d11-exclusive-fs=yes` + `target-colorspace-hint=yes`），且要 Vulkan 驱动支持。**网格多路播放时不可能每路都独占全屏。**

所以产品上必须明确：
- **单路全屏** → 支持 HDR 直通（真 HDR，不 tonemap）
- **网格多路** → 全部 tonemap 到 SDR（mpv 侧 tonemap，iptvnator 已验证 4K25 HDR10 PQ/BT.2020 全帧率可行）
- 设置面板要显式告诉用户「切到单路全屏可开 HDR 直通」，不能让用户以为网格里也有 HDR

## 1. 架构终稿（三条渲染路径，按平台/需求选）

```
                     ┌──────────────────────────────────────┐
                     │  VOLTA (Qt6 QML)                     │
                     │  core/ · engine/ · ui/               │
                     └───────────────┬──────────────────────┘
                                     │
        ┌────────────────────────────┼────────────────────────────┐
        │                            │                            │
   ┌────▼─────┐              ┌───────▼────────┐          ┌────────▼────────┐
   │ 路径 B    │              │   路径 C        │          │   路径 A'       │
   │ --wid 嵌套│              │ 进程内 libmpv   │          │ 帧拷贝回退       │
   │ (Windows) │              │ render_context  │          │ (任何平台可用)   │
   └────┬─────┘              └───────┬────────┘          └────────┬────────┘
        │                            │                            │
   mpv 进程 × N                 单进程多 handle              mpv helper 进程 × N
   完整 gpu-next                 老 vo_gpu                     完整 gpu-next
   UI 需 overlay 窗口            UI 天然覆盖                    CPU 带宽开销
```

### 1.1 选型规则（不是三选一，是按需求路由）

| 场景 | 选 | 理由 |
|---|---|---|
| **Windows 主路**（默认） | **B：`--wid` 嵌套** | 保留 gpu-next 画质；iPtvnator 已验证可行 |
| 需要 UI 无缝覆盖视频（弹窗、字幕预览、鼠标穿透） | **C：进程内 libmpv** | 无窗口层级问题，UI 直接画在上面 |
| **Linux/macOS 首版** | **C 或 A'** | X11 原生嵌套稳定性差；macOS 窗口层级对系统合成器脆弱（iptvnator 踩过 26.2 回归） |
| 视频很小 / 缩略图预览 / 特效叠加 | **C** | 无需 gpu-next，画质损失无感 |

**关键**：这三条路径封装在 `engine/` 一层后面，对 `ui/` 暴露**同一个接口**（`VideoSurface { attach(slotId, source); setFocus(bool); setRenderSize(w,h); setShaderChain(...) }`）。将来 gpu-next 的 libmpv 后端合并了，切路径只动 `engine/`，`ui/` 一行不改。

### 1.2 路径 B 的 overlay 难题怎么解（iptvnator 踩过，我们提前解）

原生窗口层级问题具体是：mpv 的子 HWND 永远在 QML 之上 → 播放列表、控制条盖不住视频。

三种解法，选一个：

| 解 | 做法 | 代价 |
|---|---|---|
| B1 | QML 窗口不透明，视频区域「挖洞」露出子 HWND；UI 画在洞外 | 视频上不能有 UI（不能用弹窗/悬停控件） |
| B2 | 独立顶层透明 overlay 窗口，跟随主窗口同步位置 | 要处理焦点、DPI、置顶、多显示器 |
| B3 | **视频区域不放原生 UI**，控制条固定在网格下方/侧边 | 最简单，牺牲「悬停出控制条」 |

**推荐 B3 打底 + B1 补**：网格布局里控制条在下方（GridPlayer 风格，本来就这样），单路模式才用 B1 挖洞做沉浸式。这跟 GridPlayer 的实际交互一致，风险最低。

**M0 必须验证**：子 HWND 在 QML 窗口里的 z-order 和 DPI 缩放（iptvnator 明确标注这条要专门测：「native-view engines position OS windows, not DOM nodes；CSS 值只在 100% 缩放时等于像素」）。

## 2. 补全：v1/v2 漏掉的东西

### 2.1 字幕

- mpv 内置 libass，字幕渲染在 mpv 侧（路径 B/C 都是），**不需要我们处理 ASS 渲染**
- 但**字幕样式必须主题化**：终端主题的字幕要用等宽字体 + 磷光绿 + 描边，默认主题用 Segoe UI + 白字
- mpv 有 `sub-style` / `sub-font` / `sub-font-size` / `sub-color` / `sub-border-size` 等属性 → 直接推
- **多路字幕同时渲染的 CPU 开销**：libass 是 CPU 渲染，每路都有字幕就是 N 份 CPU 渲染 → 背景格降级时可关字幕（`sub-visibility=no`）
- 中文字幕：mpv 用 `embeddedfonts=yes` + 系统字体，需确认 CJK 字体在 mpv 沙箱里能加载（Windows 上 mpv 加载字体有路径限制，要测）

### 2.2 播放列表语义

明确区分三种，避免用户困惑：

| 类型 | 语义 | 循环作用范围 |
|---|---|---|
| **Queue（队列）** | 播完就停 | 无循环 / 列表循环 |
| **Playlist（播放列表）** | 用户显式管理的集合 | 列表循环 = 在这个集合里转 |
| **Folder（文件夹）** | 目录扫描结果 | 列表循环 = 目录内转 |

**「全部循环」的歧义是经典坑**：`loop-playlist=inf` 循环的是 mpv 的 playlist，不是我们 UI 里的列表。所以我们**不用 mpv 的 playlist 机制**——我们自己在 `core/playlist` 管列表，每格只加载一个文件，播放结束由我们调度下一格。这样「全部循环」语义完全在我们手里，没有歧义。

### 2.3 状态持久化与恢复

- 退出时保存：窗口几何、主题、语言、画质档、布局模式、播放列表（路径 + 播放位置 + 每格的 A/B 点 + 音量 + 静音状态）
- **崩溃恢复**：如果上次非正常退出，启动时提示「上次异常退出，是否恢复会话？」
- 配置文件用 JSON（人可读、能 diff、能手改），放 `%APPDATA%/VOLTA/`
- **schema 版本号**，配置结构变了能迁移，不能迁移就备份旧的再重建

### 2.4 错误处理与诊断

三层，每层给不同的信息：

| 层 | 例子 | 用户看到 | 日志 |
|---|---|---|---|
| 引擎 | 文件不存在 / 解码失败 | 「无法解码此文件（codec: hevc, 硬件加速不可用）」 | mpv 原始 stderr + 上下文 |
| 传输 | D3D11 设备丢失 / 纹理创建失败 | 「图形设备重置中…（3 秒后自动恢复）」 | HRESULT + 恢复动作 |
| 逻辑 | A-B 点越界 / 播放列表为空 | 「B 点必须晚于 A 点」 | 断言 + 状态快照 |

**诊断导出**：设置里有个「导出诊断信息」按钮，打包一个 zip：配置、日志、mpv stderr、各路 `frame-drop-count` 快照、GPU 型号、显示器的 HDR 状态。给用户排障用，也是我们远程支持用。

### 2.5 打包与分发

- **Vulkan loader 必须随包**：`libmpv-2.dll` 硬导入 `vulkan-1.dll`，没装显卡驱动的机器上 Windows 直接拒绝加载该 DLL（jellyfin-mpv-shim 踩过，他们为此自己构建了 loader 一起分发）
- 用 `mpv-dev-lgpl` 构建（LGPL），避免 GPL 传染
- mpv 二进制**版本锁定 + 校验和**写进 manifest，启动时校验
- 打包格式：MSIX（Windows 商店）或 Inno Setup（官网下载）。**Inno Setup 更适合带 GPU 驱动依赖的场景**，MSIX 的沙盒对 GPU/音频设备有额外限制

### 2.6 硬件兼容矩阵（M0/M1 必测）

| 项 | 要求 |
|---|---|
| GPU | 至少 Intel UHD 620 级（VAAPI/D3D11VA 硬解）+ NVIDIA/AMD 独显 |
| 无 Vulkan 驱动的机器 | 必须能跑（退到 d3d11 gpu-api，或 `mpv-dev-lgpl`） |
| 无独显（核显） | 4 路 1080p 是上限，9 路 4K 不可能 |
| 多显示器 | 主副屏 HDR 状态不同 → 逐屏判断 |
| 休眠唤醒 | 唤醒后设备可能丢失 → D3D11 设备重置流程 |
| 显卡热插拔（笔记本） | eGPU 拔掉 → mpv 进程崩溃 → 重启该格 |

**「无 Vulkan 驱动」这条必须实测**，不能假设用户都有。

### 2.7 电源与发热

笔记本上 9 路视频 + 着色器 = 显卡满载，风扇狂转。措施：
- dormant 档不渲染（省 GPU）
- 窗口不可见时整个应用暂停（省一切）
- 提供「节能模式」：切到 balanced 时禁用 CRT/VHS 等逐像素 shader，只保留缩放与色彩
- 检测电池供电（Windows: `GetSystemPowerStatus`）→ 自动降档

### 2.8 无障碍

- 键盘全操作（不依赖鼠标）
- 焦点可见（终端主题的绿框 + 默认主题的蓝色 outline）
- 字幕字号可调，UI 字号可调（令牌里 `font.scale`）
- 屏幕阅读器：QML 的 `Accessible.role` / `Accessible.name` 要填
- 对比度：终端主题的 `#33ff66` on `#0a0f0a` 对比度约 12:1，远超 AA；但**默认主题的次要文字要验 4.5:1**

### 2.9 测试策略

| 层 | 工具 | 判据 |
|---|---|---|
| core/ 纯逻辑 | pytest | 布局计算、循环状态机、A-B 校验、画质档决策 **100% 覆盖** |
| engine/ IPC | 契约测试（起真 mpv 进程） | 每个属性推过去 mpv 都认；属性名拼错会红 |
| 着色器 | CI 里用 mpv 编译每个 shader | 编译失败即红；**并检查 hook 点在目标管线真的会触发** |
| 主题 | 令牌覆盖率 + 截图回归 | 见 §v2 |
| i18n | key 集合一致性 + 残留扫描 | 见 §v2 |
| 端到端 | 手工 + 录屏 | M0/M3 的性能判据靠自动化脚本跑 |

**着色器 CI 特别重要**：libplacebo 的某些 hook 点在特定缩放方向下根本不触发（`SIGMOID` 下采样时不触发），shader 写完「编译通过」不等于「会生效」。CI 要在**两种缩放方向**下各渲一帧做像素差比对。

### 2.10 可交接性（Mike 明确要的）

- `docs/` 里：架构决策记录（ADR）、模块边界说明、常见错误速查
- 每个 ADR 写清楚：背景 / 决策 / 备选 / 后果 / 何时该推翻它
- **代码里不写「为什么」只写「是什么」**——为什么写进 ADR
- 首次贡献流程：改代码 → 跑 `make check`（含全部 CI 门禁）→ 提交
- 一条命令起环境：`make dev`（拉 mpv 二进制 + 起 QML 热重载）

## 3. 里程碑（重排，M0 拆细）

| 阶段 | 产出 | 验收判据（全是数字） |
|---|---|---|
| **M0a** 路径 B 最小验证 | Qt 窗口 + 一个子 HWND + mpv 嵌进去 | 1080p60 显示，z-order 正确，2 个 DPI 缩放档都正常 |
| **M0b** 帧传输选型 | B / C / A' 三条都跑通最小 demo，量延迟 | 延迟 < 30ms；CPU 拷贝 = 0（B/C）或 < 8 GB/s（A'） |
| **M0c** 性能基线 | 9 路 760×428 + 1 路 1080p60 | 帧率全 60，掉帧 < 1%，GPU 占用 < 85% |
| **M1** 单视频完整 | 控制条 + 播放列表 + A-B + 缩略图 + 画质档 | 所有循环模式可切且正确；缩略图 500 个文件 < 20 秒生成 |
| **M2** 主题 + i18n | 两套壳 + 令牌化 + 词典 + 双门禁 | 令牌覆盖 100%；切 en 后残留汉字 = 0 |
| **M3** 网格 | 多进程多槽位 + 布局 + 焦点管理 | 4 路 1080p60 掉帧 < 1%；单格崩溃后 3 秒内自动重启 |
| **M4** 着色器 | CRT + VHS + 增强档 | 参数实时可调不重启；两缩放方向都验证生效 |
| **M5** 打磨 | 快捷键、诊断导出、设置、性能面板 | 诊断 zip 能复现问题；无操作 2 步可达任意设置 |

**M0a/M0b/M0c 是分开的**，因为它们验证的是三件不同的事。上一版把它们揉成「M0 验证」是个偷懒——验证不过时你不知道该换哪条路。

## 5. 剩下的真风险（不假装都已解决）

| 风险 | 概率 | 现在的判断 |
|---|---|---|
| 路径 B 的 z-order / DPI 问题修不动 | 中 | 有 B1/B3 兜底；iptvnator 遇到过类似问题并给出解法 |
| 帧拷贝带宽在 4K 焦点格不够 | 低 | 475 MB/s vs 16 GB/s，余量充足 |
| 9 路 4K 在核显上做不到 | **高** | 这是硬件物理限制。产品对策：明确标注推荐硬件，加「低配模式」自动降档 |
| gpu-next libmpv 后端合并后架构要重做 | 低 | 已在 `engine/` 抽象层隔离，切换成本 1–2 周 |
| 用户没有 Vulkan 驱动 | **高** | 必须实测退路，不能假设 |
| 主题令牌体系被绕过（有人直接写死颜色） | 中 | CI 硬门禁 + 截图回归双保险 |
